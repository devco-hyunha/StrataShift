## 근거 (실측)

1. 엔진은 `general.architecture` 문자열로 클래스를 고른다 (`src/poly/engine.cpp:812-817`, 밖은 throw).
2. hook 계약·`load_moe(il, false)`·`gelu_=false`는 [mixtral_class_contract.md](../rea/mixtral_class_contract.md) (AC1).
3. HF 이름 → GGUF 이름의 근거는 핀 llama.cpp `gguf-py/gguf/tensor_mapping.py`
   (`3cf03257`, `.local/llama.cpp/`): `input_layernorm`→`attn_norm`(193), `post_attention_layernorm`→`ffn_norm`(405),
   `block_sparse_moe.gate`→`ffn_gate_inp`(458, "mixtral"), `embed_tokens`→`token_embd`(16), `lm_head`→`output`(79),
   `model.norm`→`output_norm`(100), 전문가 `w1/w3/w2`→`ffn_gate_exps/ffn_up_exps/ffn_down_exps`(597/543/674).
   GGUF 이름 접미사는 `gguf-py/gguf/constants.py:1434-1469`. 엔진 쪽 이름(`attn_q.weight` 등)은
   `gemma4.cpp:197-209`, `qwen35.cpp:84-106`과 같다.
4. RoPE: 엔진의 `head_norm_rope`(kernels.hpp:149-160)는 NeoX pairing인데 **항상 RMS norm을 함께 한다**
   (kernels.cu:933-948 실읽기, `w=null`이어도 norm). Mixtral에는 Q/K norm이 없으므로 쓸 수 없다.
   엔진의 `dsv4_rope`(kernels.hpp:219-232, kernels_dsv4.cu:111-137)는 `norm=false`로 norm 없이 ggml normal
   pairing(값 i와 i+1)을 돌린다. ext_factor 0, freq_scale 1, attn_factor 1이면 YaRN 없이 `cos/sin`만 남는다
   (kernels_dsv4.cu:89-101). HF Mixtral 가중치는 half-split(i와 i+d/2) 회전 기준이므로, emit이 q/k 행을
   llama.cpp 변환기와 같은 방식으로 재배열한다(아래 §설계 2-3). q와 k에 같은 순열을 적용하면 attention 점수
   q·k는 그대로이고, V·O는 영향이 없다.
5. 라우팅: HF Mixtral = softmax → top-2 → 합으로 나눔. 엔진 `Qwen35::route`(qwen35.cpp:335-353)와
   `route_rows(..., gate 0, in_scale 1, norm true)`(qwen35.cpp:355-358)가 같은 규칙이다. contract §4의
   HYPOTHESIS(escale 기본값)는 Qwen35 route에 escale이 없음을 실읽기로 확인해 닫는다 — Mixtral도 escale 없음.

## 관련 논문·선행 자료 (0-1 논문 확인)

이 Goal은 설계 게이트를 지난 뒤(2026-10-23 09:53) 0-1 규칙이 생겨 **사후에 확인**했다(2026-10-23, 논문 본문
ar5iv HTML로 대조). 검색 키워드: "Mixtral of Experts", "rotary position embedding pairing", "MoE offloading Mixtral",

| 자료 | 참조 목적 | 대조 결과 | 연결 |
|------|-----------|-----------|------|
| Mixtral of Experts (arXiv 2401.04088) | 해석 근거 | 라우터 `y = Σ Softmax(Top2(x·W_g))_i · SwiGLU_i(x)`. top-2 logit에만 softmax를 하는 것은 우리(전체 softmax → top-2 → 합으로 나눔, qwen35.cpp와 같음)와 수학적으로 같다. | RoFormer (arXiv 2104.09864) | 해석 근거 | 원 논문의 RoPE는 이웃 쌍 (x₁,x₂),(x₃,x₄)… 회전(§3.4.3, eq. 34), θᵢ = 10000^(−2(i−1)/d). 엔진 `dsv4_rope`의 normal pairing이 이 원래 형태이고, HF 구현의 half-split은 그 변형이다. 쌍마다 독립 회전이라 q/k에 같은 순열이면 q·k 불변 → 행 재배열이 맞다. **수정 불필요** (`test_row_order_*`가 수치로 확인) | `meta/mixtral_rope.py` |
| Fast Inference of MoE LMs with Offloading (arXiv 2312.17238, §4.1 계열 2) | 개선 근거 | Mixtral-8x7B에서 attention 4-bit·전문가 2~3-bit HQQ가 유리하다고 보고하고, **"embeddings, logits, MoE gates and normalization layers"는 16-bit로 둔다.** 우리 emit은 `--dense-type Q4_K`에서 라우터 `ffn_gate_inp.weight`를 Q4_K로 양자화한다 → **수정 후보 1** | emit dense 형식 선택 |
| Examining PTQ for MoE (arXiv 2406.08155) | 개선 근거 | attention에 전문가보다 많은 비트(4-bit)를 주라는 결과. 라우터 정밀도는 다루지 않음. Mixtral은 라우팅이 고르게 퍼져 빈도 기반 비트 배분 이득이 작다. 우리 기본(전문가 Q2_0, dense Q4_K)과 방향이 같다. **수정 불필요** | AC5 양자화 프리셋 해석 |

논문 확인에서 나온 핀 소스 대조: 핀 llama.cpp `3cf03257`의 `src/llama-quant.cpp` `tensor_allows_quantization()`은
"do not quantize expert gating tensors" — `ffn_gate_inp.weight`를 양자화하지 않는다(로컬 핀 사본에는 `src/`가 없어
GitHub의 같은 커밋 원문으로 확인, 2026-10-23). 그래서 수정 후보 1은 논문(해석)과 핀 소스(확정 근거)가 같은 쪽을 가리킨다.

- **수정 후보 1 → 반영 (2026-10-23, 사용자 요청)**: Mixtral emit에서 라우터 `ffn_gate_inp.weight`를 `--dense-type`과 관계없이 F32로
  둔다(HF BF16 → F32, 층마다 4096×8 = 128 KiB). 엔진 `load_moe`는 `kAnyMat`라 F32도 받는다(llama.cpp GGUF는 원래 F32).
  gemma4 등 다른 아키텍처도 같은 문제지만 기존 산출물·테스트가 Q4_K를 전제하므로 별도 Goal로 다룬다.
- **수정 후보 1 차이 측정 (2026-10-23, `.local/p6-01/router_ab/`, git 밖)**: 라우터 가중치를 형식별로 양자화→ggml 기준
  dequant(핀 gguf-py `quants.dequantize`)한 뒤, RMSNorm된 무작위 입력 20,000개에서 top-2 선택이 F32와 달라지는 비율.
  ggml 기준 양자화기는 핀 ggml(`ggml_quantize_chunk`)을 `ggml-base.lib`에 링크한 작은 도구(`qref.exe`)로 만들었다.
  mini 라우터는 난수 가중치라 크기는 참고용이고, 방향을 보는 측정이다.

  | 라우터 형식 | 가중치 상대 오차 | top-2 바뀜 | 같을 때 gate 가중치 차 |
  |---|---|---|---|
  | F32 (수정안) | 0 | 0 | 0 |
  | Q8_0 (우리 producer) | 0.54% | 0.36% | 0.0009 |
  | Q4_K (ggml 기준 producer) | 7.0% | 5.3% | 0.011 |
  | **Q4_K (우리 producer, 지금 emit)** | **87~88%** | **48%** | 0.090 |

  엔진에서는 라우터 F32 GGUF도 `strata-shift-poly`가 rc 0으로 실행했고(라우터 F32 2개 확인), 41토큰 입력의 생성이 첫 토큰부터
  달라졌다(A `1571,1281,…` / B `1348,1348,…`). 다른 dense 행렬도 같은 Q4_K라 mini 출력 차이는 라우터만의 효과가 아니다.
- **측정 중 발견 (이 Goal 밖, 심각)**: 우리 plain K-quant producer가 ggml 기준 dequant로 보면 크게 틀린다 — 정규분포
  4096값 상대 오차 Q4_K 86~89%, Q6_K 51%, Q3_K 39%, Q5_K 29%, imatrix Q4_K 38% (기준: ggml Q4_K 7.2%, 우리 Q4_0 9.5%,
  Q8_0 0.5%). 원인 단서: `quantize_q4_k_stream`이 그룹 범위 전체를 `d·sc` 한 칸으로 잡아 코드가 0~1만 쓰인다
  (docstring의 HYPOTHESIS producer, p3-04). 기존 테스트는 바이트 형식(엔진 dequant 왕복 일치)만 보고 품질은 보지 않았다.
  `--dense-type Q4_K`(기본 권장)로 만든 모든 산출물의 dense 행렬에 영향 — 별도 Goal로 고쳐야 한다. 라우터 F32는 이것과
  별개로 유효하다(ggml 기준 Q4_K도 top-2를 5% 바꿈, 핀 llama.cpp는 라우터를 양자화하지 않음).

### 3. Mixtral 매핑과 emit (AC2)

- `meta/hf_gguf_map.py`: `MIXTRAL_LAYER_DENSE`, `MIXTRAL_GLOBAL_DENSE` (근거 §근거 3, HF 키는 fixture `key_patterns`):
  | HF (`model.layers.<L>.` 뒤) | 엔진 | 규칙 |
  |---|---|---|
  | `input_layernorm.weight` | `attn_norm.weight` | same (F32) |
  | `post_attention_layernorm.weight` | `ffn_norm.weight` | same (F32) |
  | `self_attn.q_proj.weight` | `attn_q.weight` | rope_permute (아래) |
  | `self_attn.k_proj.weight` | `attn_k.weight` | rope_permute |
  | `self_attn.v_proj.weight` | `attn_v.weight` | transpose |
  | `self_attn.o_proj.weight` | `attn_output.weight` | transpose |
  | `block_sparse_moe.gate.weight` | `ffn_gate_inp.weight` | transpose ([n_embd, n_expert], `load_moe`) |
  | 전역 `model.embed_tokens.weight` / `lm_head.weight` / `model.norm.weight` | `token_embd` / `output` / `output_norm` | transpose / transpose / same |
- `meta/expert_map.py`: `layers.<L>.block_sparse_moe.experts.<E>.(w1|w2|w3).weight` 패턴 추가 (fixture `key_patterns` 실측).
  emit은 이미 있는 `emit_per_expert`가 전문가별 텐서를 하나씩 읽어 `[in, out, NE]`로 쌓는다
  (w1 [14336,4096] → `ffn_gate_exps` [4096,14336,8], w2 → `ffn_down_exps` [14336,4096,8]).
- `derive_geometry(arch="mixtral")`: `embedding_length`(embed_tokens), `block_count`, `expert_count`(전문가 id 개수),
  `expert_feed_forward_length`(w1 shape[0]), `attention.head_count`/`head_count_kv`(q/k 행 ÷ head_dim,
  head_dim은 config.json — `read_hf_config`). guard 파일 값과 다르면 거절(기존 규칙).
- q/k 재배열 (`rope_permute`): 머리 하나의 행 `[0..d/2)`와 `[d/2..d)`를 번갈아 놓는다 — 새 행 `2j`는 옛 행 `j`,
  `2j+1`은 옛 행 `j + d/2`. head 수는 q는 `head_count`, k는 `head_count_kv` (guard). 행 단위 재배열이므로
  양자화(행마다 독립)와 섞여도 된다. 순수 함수 `quant`가 아닌 `meta/mixtral_rope.py::rope_row_order(n_head, head_dim)`
  가 행 순서만 만들고, emit이 그 순서로 행을 읽는다. 텐서 하나(q 32 MB BF16)만 살아 있다 (C1).
- `stream/emit_hf.py`: `select_arch_tables`를 arch 문자열로 고른다(gemma4 / mixtral / 기본). Mixtral 순서 표는
  `hf_emit_order.MIXTRAL_2D/MIXTRAL_1D`.
