## 한 줄 목표

`monitor/rss.py`가 Windows에서도 실제 RSS(Working Set)를 재고, 잴 수 없는 OS에서는 0이 아니라
`None`(측정 불가)을 돌려준다. `--max-rss-gb`를 줬는데 잴 수 없으면 조용히 통과하지 않고 거절한다.

## In / Out

- In
  - `monitor/rss.py`: `process_rss_bytes(pid=None) -> int | None` (Linux `/proc/<pid>/status` VmRSS,
    Windows `ctypes` `GetProcessMemoryInfo` `WorkingSetSize`, 그 밖 `None`), `current_rss_bytes()`는 자기 프로세스
  - `monitor/sampler.py`: `None` 샘플을 견딤 (`over_limit`·`rss_peak`)
  - `cli/main.py`: `--max-rss-gb`인데 측정 불가면 stderr 한 줄 + 종료 코드 2
  - `tests/test_rss_flat.py`: 측정값이 0보다 큰지 확인, 측정 불가 OS는 이유와 함께 건너뜀
  - `scripts/p5_api_smoke.py`: 엔진 프로세스 RSS를 같은 함수로
  - Windows 실측 기록: mixtral-tiny `convert --emit-gguf`의 RSS 샘플·최댓값
- Out
  - 쓰지 않는 `sample_rss()`는 지운다 (import만 있고 호출 0건)
  - `p5_api_smoke.py`의 `pgrep`·`VmPeak`·`VmSwap`(리눅스 전용 부가 값)과 엔진 실행의 Windows화 → 3e
  - `_slice_read` seek+read 방식 변경 (요청서: 다시 재서 기록만, 방식은 그대로)

## 설계

- `process_rss_bytes(pid: int | None = None) -> int | None`
  - Linux: `/proc/self/status` 또는 `/proc/<pid>/status`의 `VmRSS` × 1024 (기존과 같은 값)
  - Windows: `kernel32.GetCurrentProcess()` 또는 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION |
    PROCESS_VM_READ, False, pid)` → `psapi.GetProcessMemoryInfo(h, PROCESS_MEMORY_COUNTERS)` →
    `WorkingSetSize`. 구조체·상수는 Win32 문서 값(근거 주석). 새 의존성 없음 (`psutil` 안 씀).
  - 실패·그 밖 OS: `None`
- `Sampler`
  - `record()`는 값(`None` 포함)을 그대로 쌓는다 → JSON에는 측정 불가가 `null`로 남는다(0과 구분).
  - `over_limit()`: 마지막 값이 `None`이면 False (CLI가 미리 막으므로 한도와 `None`이 함께 오지 않음).
  - `rss_peak() -> int | None`: 측정값의 최댓값, 하나도 없으면 `None`.
- CLI: `convert --max-rss-gb N`이고 `current_rss_bytes() is None`이면
  `error: --max-rss-gb needs RSS measurement, unavailable on <platform>` + 종료 코드 2 (사용법 오류와 같은 등급).
- 출력 JSON 바이트: GGUF·pack 바이트는 그대로. `manifest.json`·`conversion.json`·stdout JSON의
  `rss_samples_bytes`·`rss_peak_bytes`는 이제 실제 값이라 실행마다 다르다.
  → 기준 해시 도구(`.local/refactor-p6-08/baseline.py`, git 밖)의 정규화에 이 두 키를 힙 값처럼 넣는다.
