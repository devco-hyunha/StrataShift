## 한 줄 목표

HF multi-shard 체크포인트(`model-00001-of-NNNNN.safetensors` … + `model.safetensors.index.json`)을
스트리밍으로 엔진 GGUF emit 입력으로 받아, 단일 파일 입력과 **바이트 동일**한 산출물을 얻고
엔진 체인 acceptance를 통과한다.

## 근거 계약 (pin c566ff4, read-only)

1. **HF index.json 규격** (HF transformers 공개 컨벤션):
   `{"metadata": {"total_size": N}, "weight_map": {tensor_name: "<shard file>.safetensors"}}`.
   tensor 이름 → shard 파일; 오프셋은 각 shard 헤더의 `data_offsets`(data_start 기준).
2. **엔진 shard 검증 규칙** (GgufModel, `include/strata/artifact/gguf_reader.hpp:520-562`,
   `include/strata/artifact/gguf_split.hpp:18-50` — 미러링 대상):
   - shard 번호 패턴 `-NNNNN-of-MMMMM` (5자리), metadata shard(00001) 우선,
     **누락 shard는 이름을 지목하는 오류** (gguf_split.hpp:44-46).
   - shard 간 디렉토리가 총계와 안 맞으면 거부 (tensor 디렉토리 합 != split.tensors.count,
     gguf_reader.hpp:524-526) → 우리 게이트: weight_map ↔ shard 헤더 전사 전수 일치.
   - **한 tensor가 두 shard에 있으면 거부** (gguf_reader.hpp:536-540) → 우리 게이트 동일.
   - tensor payload가 자기 shard 파일 안에 들어야 (in_bounds, gguf_reader.hpp:557-562)
     → 우리 게이트: parse_header의 data_start+max_end ≤ file_size 검증 재사용.
3. **safetensors 헤더** (기존 `ingest/safetensors_header.py`, p1-01): shard마다
   `[u64][JSON][8B-aligned data]`; `data_offsets`는 shard별 data_start 기준.
4. **스트리밍 위생 (p4-01 VERIFIED)**: mmap 금지 — mmap은 touched page를 상주시켜
   page cache가 shard 크기로 성장해 OOM (RC=137 실측). fadvise DONTNEED도 불충분
   (p4-01 기록: 9p/ext4 모두에서 OOM, fadvise에도 불구). emit reader는 shard handle
   캐시 + seek+read — 한 slice만 heap에 (C1/C2, 실측 peak 126 MB).

## 설계

```text
[CLI model 인자]
  ├ 단일 .safetensors → parse_header (기존 경로, 변화 없음)
  └ 디렉토리 또는 shard 파일 → shard_index.py
       [1] index.json 위치 해석 (dir/index.json, dir/model.safetensors.index.json,
           shard 파일의 옆 디렉토리)
       [2] weight_map 파싱 + shard 파일 전수 존재 확인 (누락 → 이름 지목 오류)
       [3] shard별 parse_header (헤더만 — C1/C2)
       [4] 검증 게이트 (엔진 미러):
           - weight_map tensor ↔ shard 헤더 전사 전수 일치 (양방향)
           - 한 tensor 두 shard → 거부
           - shard 헤더 tensor가 weight_map에 없음 → 거부
           - total_size == Σ shard payload bytes
       [5] ShardedModel: TensorMeta + shard_path; shard별 data_start 레지스트리;
           abs_offset(t) = shard_data_start[shard] + t.data_offsets
[emit/convert] tensor별 shard 파일 handle (open/seek/read, fadvise DONTNEED),
              한 slice만 heap에 (C1/C2)
```

- 데이터 구조: `TensorMeta`에 `shard: str = ""` 추가 (빈 값 = 단일 파일 모델 — 기존
  parse_header/테스트 무영향). `ModelMeta`에 `shard_data_start: dict[str,int]` 추가.
  `expert_map`/`hf_gguf_map`/`derive_geometry`는 name/shape/dtype/offsets만 읽으므로 무변경.
  emit/convert의 오프셋 해석이 shard 레지스트리 경유로 바뀐다.
- FOLDER_STRUCTURE: `src/stratashift/ingest/shard_index.py` (ingest 책임 — 헤더/shard 해석).
- CLI: `convert`/`inspect`의 model 인자가 디렉토리면 shard 경로 자동. `--hf-emit` 게이트 유지.

**원인 규명 (root cause, 같은 Goal에서 닫음 — 3건):**
1. `p4_shard_split.gen_tensor`가 fused gate_up payload를 `bytes +=`로 누적 → 6.7 GB
   2차 누적 (98% CPU, blob 99 MB에서 정지). `tensor_chunks` 제너레이터로 expert-run
   스트리밍 교체 (p4-01 builder convention, 바이트 동일).
2. `chain_a` 인자 순서: GGUF를 safetensors 입력으로 전달 → `parse_header`가 GGUF를
   safetensors로 파싱해 "header truncated" FAIL. 시그니처 `(st, guard, out_dir)`에
   맞게 shard 디렉토리를 입력으로 전달하는 것으로 수정.
3. 전수 pytest에서 `test_safetensors_gguf_engine_chain` OOM (RC=137):
   `iter_tensor_payloads`가 tensor payload 전체(3.35 GB F32)를 heap에 yield하고
   `continue` 경로가 이전 blob을 해제하지 않아 transient 2 blobs ≈ 6.7 GB > available
   RAM. `cmd_convert`를 entry 메타데이터(shape×dtype) 게이트 + seek+read로 교체 —
   Q2_0-shaped tensor만 slice로 읽음. `stream/mmap_reader.py` 삭제(유일한 caller 제거,
   MODULE_DESIGN 동기). 재검증: 체인 단독 GREEN(3 passed/219.21s) 후 전수 GREEN.
